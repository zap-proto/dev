# Post-Quantum

ZAP runs unchanged over **Z-Wing**, the canonical post-quantum secure channel for the Lux network. Z-Wing is **one construction**, not a menu of suites — two endpoints either speak Z-Wing v1 or they don't talk. No negotiation, no downgrade, no cipher suite ID byte to fingerprint.

## What Z-Wing is

Z-Wing is a *composition*, not a new cryptographic primitive. It bolts together vetted pieces and exposes a `net.Conn` so application protocols (e.g. ZAP RPC) run unchanged.

```
┌─────────────────────────────────────────────────────────────────┐
│ Z-Wing v1                                                       │
│                                                                 │
│   KEM        IETF X-Wing  (X25519 + ML-KEM-768, SHA3-256        │
│              combiner — bit-for-bit interop with any            │
│              draft-connolly-cfrg-xwing-kem peer)                │
│   Identity   Ed25519 + ML-DSA-65 hybrid signatures              │
│              (both must verify; either-or compromise still      │
│              fails forgery)                                     │
│   AEAD       ChaCha20-Poly1305, sequence-numbered nonces        │
│   Transport  any net.Conn (TCP today; RNS link in LP-9702)      │
│                                                                 │
└─────────────────────────────────────────────────────────────────┘
```

The cryptography at the KEM layer is **real IETF X-Wing** byte-for-byte. The Lux value-add lives in the layers *above* the KEM — hybrid identity bound into the transcript, single canonical wire format, RNS-routed transport — not in forking the KEM itself.

Repo: [github.com/luxfi/zwing](https://github.com/luxfi/zwing).

## X-Wing vs. Z-Wing — they aren't competing suites

A common mix-up:

- **X-Wing** is a **KEM primitive**. It is the IETF draft hybrid KEM: X25519 + ML-KEM-768 combined via SHA3-256 with a fixed label string. That's it — just the key exchange.
- **Z-Wing** is the **full secure channel** that uses X-Wing as its KEM. Z-Wing adds identity binding (hybrid sigs into the handshake transcript), domain-separated channel keys (`lux.zwing.v1/i2r`, `/r2i`), AEAD record framing, and routing.

You don't pick "X-Wing" or "Z-Wing." You speak Z-Wing, which uses X-Wing.

## Handshake (1-RTT)

```
Initiator → Responder   HandshakeInit
    [2 BE idLen][IdentityPublic bytes][2 BE sigLen][hybrid signature]

Responder → Initiator   HandshakeResponse
    [XWingCiphertextSize bytes: ML-KEM ct || X25519 ephemeral pk]
    [2 BE encLen][AEAD-sealed responder identity + signature]
```

- The initiator signs `(label ‖ IdentityPublic)` so a passive observer can't lift the public identity onto another protocol.
- The responder signs the **transcript hash** covering the initiator's public identity AND the X-Wing ciphertext, binding the signature to the session.
- The responder's identity is encrypted under an HKDF-derived key from the X-Wing shared secret, so passive observers don't learn the responder's long-term identity.
- The responder is the **encapsulator** (it sends `ct_X`). The initiator is the **recipient** of the encapsulation.

`IdentityPublic` is fixed-layout, 3200 bytes total:

```
[Ed25519 pk: 32][ML-DSA-65 pk: 1952][X-Wing pk: 1216]
                                    (= ML-KEM-768 pk 1184 ‖ X25519 pk 32)
```

## X-Wing combiner (IETF spec, exact)

```
shared_secret = SHA3-256( "\./" || "X-Wing" || ss_M || ss_X || ct_X || pk_X )
```

| Input | Bytes | Source |
|---|---|---|
| `"\./"` | 3 | label prefix |
| `"X-Wing"` | 6 | ASCII protocol name (IETF spec) |
| `ss_M` | 32 | ML-KEM-768 shared secret |
| `ss_X` | 32 | X25519 shared secret |
| `ct_X` | 32 | X25519 ephemeral pk from encapsulator |
| `pk_X` | 32 | X25519 static pk of recipient |

The label is `"X-Wing"`, not `"Z-Wing"`. The point of using the IETF KEM is to interop with any X-Wing peer; rebranding the combiner would break interop and add zero security.

## Channel keys

After the handshake:

```
keyI2R = HKDF-SHA256(shared, "lux.zwing.v1/i2r", 32)
keyR2I = HKDF-SHA256(shared, "lux.zwing.v1/r2i", 32)
```

Each direction gets its own ChaCha20-Poly1305 key. Nonce = 12 bytes: high 4 zero, low 8 are the big-endian sequence counter. A 64-bit counter lasts 5.8e11 years at 1 record/ns; exhausting it returns `ErrSequenceExhausted`.

The `lux.zwing.v1` HKDF info string is where the Lux value-add lives — domain-separated from any other system that might also use IETF X-Wing.

Forward secrecy: the X25519 ephemeral inside X-Wing. The ephemeral private key and intermediate `ss_M` / `ss_X` are zeroed after combination.

## Using Z-Wing under ZAP

ZAP RPC runs on top of Z-Wing's `net.Conn` — any existing ZAP service gets PQ on the wire by swapping the dialer:

```go
import (
    zap   "github.com/zap-proto/go"
    zwing "github.com/luxfi/zwing"
)

id, _ := zwing.GenerateIdentity()
raw, _ := zwing.Dial(ctx, "host:9999", &zwing.Config{LocalIdentity: id})
zapConn := zap.NewConn(raw, nil)
// existing ZAP code unchanged
```

Server:

```go
ln, _ := zwing.Listen(":9999", &zwing.Config{LocalIdentity: id})
for {
    raw, _ := ln.Accept()
    go handle(zap.NewConn(raw, nil))
}
```

Default port: **TCP 9999** (canonical Lux ZAP port).

## What Z-Wing is *not*

- **Not a competitor to X-Wing.** It uses X-Wing.
- **Not a triple-hybrid with Classic McEliece.** Just ML-KEM-768 + X25519 via the IETF combiner.
- **Not a ZK / SNARK / P3Q channel.** P3Q is a separate Lux EVM precompile for ZK proof verification at the contract layer; Z-Wing is at the transport layer. Different concerns.
- **Not configurable.** No cipher negotiation. One construction, take it or leave it.

## Browser, edge, and Lux

| Where | Path |
|---|---|
| Browser / WASM | [`@zap-proto/wasm`](https://www.npmjs.com/package/@zap-proto/wasm) speaks `wss://` to a server-side ZAP. The Z-Wing handshake terminates at the server (browsers can't dial raw TCP). For browser-edge clients you trust a TLS hop, then Z-Wing inside it. |
| Cloudflare Worker / Deno / Bun | The WASM build runs in V8 isolates. Workers hold persistent Z-Wing connections to origin ZAP and serve `fetch()` from browsers. See [transports → ZAP at the edge](/docs/transports#zap-at-the-edge-workers--deno--bun). |
| Lux network (validator-to-validator) | Native Z-Wing on TCP 9999 — production, mandatory PQ on every consensus path. |
| Service-to-service inside a Lux cluster | Native Z-Wing — same as above, no TLS in front. |

## Identity rotation

Identities are hybrid keypairs (Ed25519 + ML-DSA-65). Z-Wing doesn't pin a single identity per host — you can rotate by handing a new `Config.LocalIdentity` to the next `Dial`/`Listen`. Capability tokens (returned from [native ZAP RPC](/docs/protocols/native) methods) are signed under your identity's hybrid sig, so a quantum-capable adversary can't forge them even retroactively.
