# Post-Quantum

ZAP is PQ-ready by default. Every transport handshake runs a **hybrid KEM** that's secure as long as *either* the classical primitive (X25519) *or* the lattice primitive (ML-KEM-768) is unbroken. You don't need to opt in; you need to opt *out* if you want classical-only.

## The three suites

| Suite | KEM | Signature | When |
|---|---|---|---|
| Classical | X25519 | Ed25519 | Disabled by default in 1.0; available for low-resource embedded |
| **X-Wing** (default) | X25519 + ML-KEM-768 | Ed25519 + ML-DSA-65 | Default for every new connection from ZAP 1.0 |
| **Z-Wing** | X25519 + ML-KEM-1024 + Classic McEliece | Ed25519 + ML-DSA-87 + SLH-DSA | Belt-and-suspenders, opt-in via `WithPQSuite(zap.SuiteZWing)` |

### X-Wing (the IETF hybrid)

X-Wing is the **IETF-draft hybrid KEM** — `X25519` + `ML-KEM-768`, combined with a secure-by-construction KDF. The combined shared secret is secure as long as *one* of the two is. This is the same construction Anthropic, Cloudflare, and Apple's iMessage PQ3 have converged on for client-server key agreement.

ZAP's wire spec pins X-Wing's exact KDF and label string, so two ZAP implementations interop bit-for-bit regardless of which crypto library they vendor.

```go
import zap "github.com/zap-proto/go"

// X-Wing is the default — no flag needed
client, _ := zap.Dial(ctx, "zap://service.example:9000")

// Explicit:
client, _ := zap.Dial(ctx, "zap://service.example:9000",
    zap.WithPQSuite(zap.SuiteXWing),
)
```

### Z-Wing (ZAP's belt-and-suspenders)

Z-Wing is **ZAP's own hybrid** for adversaries who don't trust *any* single PQ primitive. It triples up:

- `X25519` — classical, broken only by a CRQC
- `ML-KEM-768` (or `ML-KEM-1024`) — lattice, NIST Round 4 winner
- `Classic McEliece` — code-based, conservative choice with the longest analysis history

Combined via the same X-Wing-style KDF, extended to three inputs. Secure as long as *any one of the three* primitives is.

Trade-off: handshakes are bigger (~1 MiB McEliece public key on first connect; cached after) and slower (~3-5 ms vs. X-Wing's ~0.6 ms on a modern x86). Worth it for archival traffic, court-grade audit logs, and roots-of-trust. Not for high-volume inner-loop RPC.

```go
client, _ := zap.Dial(ctx, "zap://service.example:9000",
    zap.WithPQSuite(zap.SuiteZWing),
)
```

There's a formal proof in [zap-proto/papers](https://github.com/zap-proto/papers) — *Z-Wing IND-CCA2-AKE under triple-hardness assumptions* — that bounds Z-Wing's combined advantage by the minimum of the three component advantages.

## Signatures

Identity signatures (peer DIDs, capability tokens, attestations) use a hybrid:

- **Default**: Ed25519 + ML-DSA-65 (NIST Round 4 Dilithium2, FIPS 204)
- **Z-Wing**: Ed25519 + ML-DSA-87 + SLH-DSA-SHA2-256s (FIPS 205, stateless hash-based)

Both signatures must verify; failure of either rejects the message. Mirror of Bouncy Castle's `Composite-ML-DSA`.

```go
identity := zap.GenerateIdentity()  // hybrid Ed25519 + ML-DSA-65 by default

// Z-Wing identity with hash-based fallback
identity := zap.GenerateIdentity(zap.WithSuite(zap.SuiteZWing))
```

## How it composes with capabilities

Capability tokens (the references you return from a [native ZAP RPC](/docs/protocols/native) method) are signed by the issuing peer's identity. When you upgrade from classical to X-Wing or X-Wing to Z-Wing, *existing capability tokens stay valid* because they're signed under your identity's lifetime hybrid key — a quantum-capable adversary can't forge them, even retroactively.

## What's standardized vs. ZAP-specific

| | Standardized | ZAP-specific |
|---|---|---|
| X-Wing KEM | IETF draft-connolly-cfrg-xwing-kem-06 | bit-for-bit |
| ML-KEM | NIST FIPS 203 | bit-for-bit |
| ML-DSA | NIST FIPS 204 | bit-for-bit |
| SLH-DSA | NIST FIPS 205 | bit-for-bit |
| Classic McEliece | NIST Round 4 | bit-for-bit |
| **Z-Wing combiner** | — | ZAP-specific (paper in [zap-proto/papers](https://github.com/zap-proto/papers)) |
| Hybrid signature | Composite-ML-DSA (draft) | bit-for-bit |
| Transcript binding | TLS 1.3-style label tree | adapted for ZAP framing |

ZAP doesn't invent new crypto — it composes vetted primitives in a published, auditable way. Every choice is replaceable: when ML-KEM is replaced by a future NIST winner, X-Wing-N rolls forward without breaking the wire format.

## Migration ladder

```
classical-only        →   X-Wing             →   Z-Wing
(legacy, opt-in)          (default 1.0)          (high-assurance)
```

You move forward by setting a per-service minimum suite:

```go
srv := zap.NewServer(
    zap.WithAddr("zap://0.0.0.0:9000"),
    zap.WithMinSuite(zap.SuiteXWing),  // refuse classical-only peers
)
```

Old clients see a clear handshake-rejection error referencing the required suite. Roll out: turn on X-Wing-or-better in observation mode (log mismatches), then enforce.
